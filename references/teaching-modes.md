# 教学模式

先从 curriculum.md 或当前任务判断 Block 类型，只采用对应模式。所有模式都遵守“先建立框架，再检索和迁移”，但先讲、先问还是先实验不同。

## 系统型

适用：产品结构、完整链路、RAG 链路、工具调用、Agent、Memory、可观测性等。

1. 用一个用户目标开场。
2. 画出输入、处理、输出和控制者的信息流。
3. 逐个说明模块职责与“不负责什么”。
4. 用一次错误沿链路反查源数据、工具返回、模型输入、模型输出和最终展示。
5. 检索题要求学习者重建链路；迁移题换一个产品，不复用原案例答案。

不要把实现视为永远固定的直线。明确循环、分支、重试、追问、人工确认和状态恢复出现在哪里。

## 机制型

适用：Token、上下文窗口、训练阶段、采样参数、Embedding、模型规格等。

1. 先直接给一句话定义，明确“是什么”和“不是什么”。
2. 用简短机制图展示输入如何变成输出。
3. 对比最容易混淆的相邻概念。
4. 给一个数字例子、微型实验或可观察现象。
5. 说明它如何影响产品质量、成本、速度或选型。
6. 最后用两到三道短题闭卷检查。

不要一开始用连续业务题让学习者猜出新概念。类比只用于建立直觉，随后必须回到真实机制，指出类比失效处。

## 实验型

适用：Prompt、RAG、API、流式输出，以及任何需要亲眼观察中间结果的主题。

1. 先给足以运行实验的最小机制。
2. 明确实验变量、保持不变的条件和预期观察。
3. 展示真实输入、中间状态和输出；有工具时实际运行，没有工具时使用透明的小样本模拟。
4. 一次只改变一个关键变量。
5. 让学习者先解释现象，再给结论。
6. 把实验现象与生产边界区分开，不能用一个小实验证明普遍规律。

实验应尽量短、便宜、可重复。不要为了“动手”引入与学习目标无关的环境配置。

## 工程型

适用：成本、延迟、吞吐、并发、推理服务、缓存、量化和压缩。

1. 先定义指标和单位。
2. 给出最小计算或系统瓶颈图。
3. 让学习者计算、比较或定位故障。
4. 加入一个反直觉边界，例如“激活参数少不等于显存只存激活参数”。
5. 把理论估算与真实实测分开，列出会改变结果的运行条件。
6. 迁移题应要求做方案选择并说明需要补测的数据。

不要只背指标定义，也不要只给无法校验的经验结论。

## 判断型

适用：模型选型、开放权重与 API、微调决策、评测、安全、隐私和综合取舍。

1. 明确目标、约束、风险和可逆性。
2. 给出至少两个可行方案，不预设技术越复杂越好。
3. 要求学习者给结论、依据、缺失证据和验证方法。
4. 用反例挑战绝对化判断。
5. 区分模型可以建议什么、确定性系统必须控制什么、何时需要人工。
6. 结论使用“在这些前提下优先选择”，不要包装成脱离条件的通用答案。

涉及真实外部操作时，教学可以分析流程，但不能把讨论自动扩展成执行权限。

## 追问与纠偏格式

学习者回答后，按需要使用以下紧凑结构，不必机械显示标题：

1. 判断：哪些项正确、部分正确或错误。
2. 关键修正：只先修正最影响后续理解的一到两个点。
3. 为什么：用因果链、数据流、计算或反例说明。
4. 检查：只问尚未证明掌握的边界。

若学习者提出一个好问题，不要把它当作打断。先判断它属于当前 Block、前置知识还是后续专题：

- 当前 Block：回答并纳入掌握检查。
- 前置知识缺口：补最少的前置内容后回来。
- 后续专题：给足以继续当前学习的边界，并记录到后续清单，不展开整章。
